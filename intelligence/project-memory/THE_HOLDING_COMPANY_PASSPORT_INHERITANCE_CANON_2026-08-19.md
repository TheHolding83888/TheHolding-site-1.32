# THE HOLDING — COMPANY PASSPORT INHERITANCE CANON
## 2026-08-19 · reusable presentation + onboarding memory

## Purpose

Every completed company should make the next company easier to onboard and harder to regress. Public Passport work is reusable operating knowledge, not one-off polish.

A new company must inherit the strongest current production presentation contract for every mechanism it reuses, just as it inherits the strongest current economic, Productivity and Rewards capability.

## 1. Core inheritance law

For Company #011 and every company after it:

`mechanism fingerprint → strongest production precedent → full economic capability → canonical public projection → parity verification → resolve only the true delta`

If a new company uses a mechanism already known by The Holding, its Passport must not fall back to weaker labels, weaker state semantics, duplicate rows, missing rate badges, or older layout behavior.

## 2. Canonical productive identity language

When the productive mechanism is proven, prefer:

`Protocol · productive asset / strategy`

Current examples include `Aerodrome · veAERO`, `Velodrome · veVELO`, `Curve · veCRV`, `Frax · veFRAX`, `Yield Basis · veYB`, `Pendle · sPENDLE`, `f(x) Protocol · veFXN`, `Liquity · staked LQTY`, `Venice · sVVV`, `Resupply · staked RSUP`, `Stake DAO · 4pool stables`, and `Convex · staked cvxCRV`.

More-specific proven strategy identity may override the generic productive-asset form when it carries real meaning, for example `Velodrome · 40 Acres`.

Reserve/non-productive assets remain concise (`BTC`, `ETH`, etc.). Unknown identity must not be guessed for symmetry.

## 3. Cross-surface parity

The same productive identity should be recognizable across Balance Sheet · Strategies, Accrued Rewards / unified Rewards Drawer, Productivity rate capsules, and any strategy-specific public detail surface.

The UI may expose different state details in each place, but it must not make one mechanism look like unrelated assets because of naming drift.

## 4. Reward-state inheritance

All future companies inherit the unified Rewards vocabulary:
- `Unclaimed` = separately claimable accrued value;
- `Compounded` = embedded/reinvested/locked earned value;
- `Pending / Warming` = known mechanism whose exact current measurement is incomplete;
- unknown != zero.

Reference APR/APY remains separate from earned amount and claimability. Do not create protocol-specific mini-ledgers when the canonical unified drawer can represent the state.

## 5. Rate-badge inheritance

Known productive mechanisms inherit the canonical Passport rate presentation: measured rate → `APR <rate>` / `APY <rate>`; unresolved supported rate → `APR Pending` / `APY Pending`; reserve assets get no synthetic rate badge; mobile uses the shared two-row title/value+rate composition; accepted desktop/laptop geometry remains unchanged unless explicitly redesigned.

## 6. Full-registry parity audit

Whenever a presentation convention is improved for one company, check all existing companies that use the same mechanism family.

Do not assume a production data refresh fixes a renderer-level gap. Verify both canonical generated data and the shared/public renderer.

PR #152 and PR #153 established this lesson directly: Rewards data already carried specific protocol/asset labels while the shared Passport renderer could still downgrade some Aerodrome/Velodrome rows to generic protocol names.

## 7. Promotion rule

A meaningful company-specific fix is not finished until its reusable lesson is promoted where appropriate into shared renderer/adapter logic, verifier contracts, project-memory canon, onboarding reuse rules, and automatic materialization paths.

The goal is that the next company receives the improvement automatically instead of requiring the owner to notice and request the same correction again.

## 8. New-company definition of done

A new Company Passport is incomplete if a known mechanism has weaker public behavior than its strongest existing precedent without an explicit semantic reason.

Before closure verify: productive identity label parity; Balance Sheet ↔ Rewards identity consistency; Unclaimed/Compounded/Pending semantics; APR/APY binding and null-safe Pending behavior; no duplicate strategy/reward rows; current responsive Passport canon; automatic refresh from canonical state; regression guards.

Compact rule: **solved mechanism = reusable economic capability + reusable public presentation + verifier + memory.**
