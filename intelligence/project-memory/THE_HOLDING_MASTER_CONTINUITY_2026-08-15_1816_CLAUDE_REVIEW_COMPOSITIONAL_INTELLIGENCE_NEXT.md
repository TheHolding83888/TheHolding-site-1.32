## 3. EXTERNAL CLAUDE REVIEW — PRIMARY CRITIQUE

The owner provided a deep hard-review response from Claude and asked that it be absorbed critically rather than accepted mechanically.

Claude's single strongest architectural critique:

> The current Intent Contract exposes `intent` as a fixed enum, so a model can only map natural language into capabilities that already exist in the deterministic router. A highly accurate model could therefore achieve excellent intent-match scores while the product still feels like a dashboard with a better translator.

Claude's proposed correction is to let the language-understanding layer express a **decomposition of the question into verifiable domain primitives**, including the ability to state that a required primitive is missing.

Representative concept:

```json
{
  "intent": "unsupported-decomposed",
  "decomposition": [
    {"object": "companyPurpose", "entity": "Monetra.eth"},
    {"operation": "compare"},
    {"object": "currentStrategyBook", "entity": "Monetra.eth"}
  ],
  "missingPrimitive": "companyPurpose"
}
```

The critical insight is NOT the exact schema above. The insight is:

**UNKNOWN should become structurally informative.**

Instead of only saying "unsupported", the OS should be able to determine:

- which conceptual pieces the question requires;
- which pieces are available;
- which primitive is missing;
- whether the question can be partially answered without semantic fraud.

This turns Owner Unknown from a static failure list into evidence about what domain object the system should build next.

## 6. WHAT WE ACCEPT FROM CLAUDE

### 6.1 Accept: move from fixed-intent classification toward compositional understanding

This is now the primary architecture correction **before further model shadow benchmarking**.

Future language understanding should be able to express the structure of a question, not merely choose a menu item.

The contract should remain bounded to the **question plane**, never the answer/source/confidence/authority plane.

Likely safe future fields, introduced incrementally and only when justified:

- `operation`
- `scope`
- `decomposition[]`
- explicit missing primitive semantics
- later, if proven necessary: aggregation / historical interval / comparison basis / causality requested / explanation depth / conceptual domain.

Do NOT add all fields at once. Capability must grow faster than complexity.

### 6.2 Accept: add false-UNKNOWN as the symmetric epistemic metric

Current canonical evaluation strongly protects against false confidence:

`false-MEASURED = 0`

But after v1.2A the mirror failure becomes important:

> data/capability exists, but Ask incorrectly refuses or returns UNKNOWN.

A new metric / corpus contract must distinguish:

- correct UNKNOWN because a primitive is genuinely missing;
- false UNKNOWN where existing evidence could answer the question.

This should become a first-class release-quality signal before model promotion.

### 6.3 Accept: compound + multi-turn questions are a major missing evaluation surface

New evaluation pressure should include questions such as:

- compare two companies and explain what changed;
- combine timeframe + company + metric + significance;
- resolve a follow-up that depends on the previous turn;
- ask a compound question containing both answerable and unsupported subparts.

These are much more representative of "operational intelligence" than more variants of single-metric queries.

### 6.4 Accept: contradiction / freshness pressure is needed

Later evaluation should intentionally include stale vs fresh or disagreeing evidence and require the system to surface the conflict rather than silently choose an attractive answer.

### 6.5 Accept: deterministic router should eventually become fallback/baseline, not a second endlessly-growing language system

Do NOT freeze it immediately.

Promotion criterion should be measured:

When a model-assisted understanding path beats deterministic routing on fresh unseen failing classes while maintaining Semantic Safety / false-MEASURED / false-UNKNOWN boundaries, stop adding ordinary language patches to the deterministic router. From that point it becomes:

- fallback;
- baseline;
- safety reference;
- known-command path.

New work should add domain capabilities, not duplicate language parsing in two stacks.

### 6.6 Accept as a future synthesis guard: Numeric & Entity Containment

When model-based explanation/synthesis is eventually allowed, every numeric/entity/date claim should be deterministically traceable to the supplied fact set or rejected.

This is a strong future boundary because it changes the rule from "trust the model not to hallucinate" to "allow only verifiable generated claims".

Do not implement this prematurely before the underlying compositional understanding and evidence sets are stable.

### 6.7 Accept: complexity itself needs measurement

Claude correctly noted that the project law:

`capability must grow faster than complexity`

currently has no numerical operational indicator.

Candidate future engineering metrics:

- median time/commits from gap discovery to proven new capability;
- number of patches needed to maintain old capability after each new release;
- number of permanent orchestration/evaluator surfaces;
- regression count per capability release.

Do not Goodhart these into a single score. Use them as maintenance signals.

## 7. WHAT WE MODIFY / REJECT FROM CLAUDE

### 7.1 Modify strongly: Realised Cash Flow is NOT simply claim + withdraw

Claude argued that Realised Cash Flow can be derived directly from onchain claim / withdrawal events and therefore one Owner Unknown gap may already be closable.

We accept the broader point that much of the necessary data may be reconstructible onchain.

We reject the simple semantic equation:

`Realised Cash Flow = sum(claim + withdraw)`

Reason:

- a withdrawal can be return of principal;
- a withdrawal can be internal rotation;
- wrapper redemption can be a position transformation;
- bridge movements can be internal;
- stable-to-stable swaps are not income;
- claim events can represent reward income but may still need boundary/economic classification;
- distributions to the owner differ from realised income retained by the company.

The correct direction is a canonical **boundary-flow / realised-income ledger** capable of distinguishing at least:

- external contribution;
- external distribution;
- realised protocol income / claim;
- principal return;
- internal deposit/withdraw;
- wrapper mint/redeem;
- internal strategy rotation;
- matched bridge;
- gas / operating cost where methodologically relevant.

This is consistent with the existing Monetra Contribution Ledger direction and should be generalized carefully rather than solved with a naïve event sum.

Therefore `owner-productivity-vs-cashflow` remains UNKNOWN until the canonical ledger/methodology is actually proven.

### 7.2 Do not accept "any paid API for a few dollars" as the immediate answer

The owner explicitly prefers no GitHub/model payment at this stage and cannot pay GitHub for Copilot Pro.

The architecture is provider-neutral specifically so that no paid provider becomes a hidden dependency.

Use free/available provider access for development where possible; do not add a paid OpenAI/Anthropic/etc. secret without explicit owner authorization.

### 7.3 Do not broaden model authority merely because reasoning is useful

Claude's useful reframing is:

We accept this as a direction for explanation/synthesis/hypothesis stages.

But current production authority boundaries remain unchanged. Verification gates must be implemented before any wider model role is promoted.
