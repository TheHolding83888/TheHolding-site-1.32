# 6. INVESTOR-FIRST INFORMATION HIERARCHY

The owner explicitly wants the portal to be useful not only for browsing but for an investor who wants to understand cash generation simply.

A physical property should allow a person to understand within seconds:

1. **Minimum Entry** — how little capital is required to enter;
2. **What You Own** — share/token/project/title structure;
3. **Income** — does the asset currently produce a cash-flow-like economic stream?;
4. **Return** — exactly what metric the source publishes;
5. **Distribution** — cadence / payout model where known;
6. **Value** — property/project/share valuation where source-supported;
7. **Status** — cash flowing / available / under construction / sold / etc.;
8. **Freshness** — when the observation was checked;
9. **Source** — where the user can reproduce the claim.

Preferred simple visual headline:

`Minimum Entry · Income · Return · Distribution`

with deeper detail below.

Do not turn investor usefulness into accounting complexity on the first screen.

# 7. RETURN / INCOME SEMANTIC LAW

Never rename every percentage to `APR` just because that is familiar in crypto.

Examples:

- Lofty may publish `Avg. Rental Yield`;
- Reental may publish `Estimated Annual Return`;
- another provider may expose a rental yield, projected IRR, distribution rate or other source-specific metric.

The UI can have a common section called **Income** or **Return**, but must preserve the exact source terminology underneath.

Hard boundaries:

- `Avg. Rental Yield != generic APR`;
- `Estimated Annual Return != realised yield`;
- `projected return != realised cash flow`;
- `minimum entry != total property/project value`;
- `claimable/accrued != realised`, if such concepts appear later.

For digital land:

> **No verified intrinsic income tracked**

is preferable to synthetic `0% yield`.

If a virtual-world parcel later gains verified lease/ad/experience revenue, the same Income Layer can expand to it.

# 9. SOURCE-FIRST / FREE-FIRST DATA STRATEGY

Realty should not require a paid CoinGecko subscription to understand property markets.

Preferred source order depends on the fact:

1. canonical onchain contracts/events where the economic fact genuinely lives onchain;
2. official marketplace / issuer / protocol first-party source;
3. official public API/feed when terms permit;
4. explicitly licensed/partner feed later;
5. high-quality source-market observation with clear provenance;
6. external research/discovery only as a lead, not automatic canonical truth.

For token-to-USD conversion:

- first preference: source already publishes exact USD for that observation;
- otherwise reuse an existing verified The Holding Market Data/oracle lane where appropriate;
- do not build a duplicate Realty-only token pricing engine merely for convenience.

CoinGecko may remain a possible fallback elsewhere in The Holding, but Realty must not architecturally depend on a new paid CoinGecko key.

Important nuance:

> public blockchain data can be observable, but a hosted RPC/indexer/API still has its own Terms/rate limits. Right to underlying public data is not identical to right to every access channel.

# 10. SOURCE GOVERNANCE / LEGAL-RESILIENCE MODEL

The owner correctly raised the issue before public/commercial scale: public visibility does not automatically mean unrestricted commercial scraping/republication.

Current operating response is **not** to freeze product development.

Instead Realty separates:

- factual observation;
- access method;
- media rights;
- commercial use;
- source routing.

Canonical machine-readable file:

`/realty/data/source-governance.json`

Public transparency surface:

`/realty/sources/`

The governance registry can record:

- source class;
- Terms URL/check date;
- automation policy;
- media policy;
- current Realty use mode;
- commercialization gate;
- attribution needs;
- future partner/API status.

Current reviewed lesson from major lanes:

- Lofty Terms contain restrictions around automated data mining/scraping and protect site content/media;
- Reental Terms create commercial/content-use constraints relevant to an aggregator/competitor context;
- OpenSea restricts unauthorized automated scraping and commercial API use may require specific permission/terms;
- The Sandbox also restricts automated scraping/mining.

Therefore do **not** build a naive mass scraper that mirrors competitor databases.

The preferred mature model is:

`official permission / API / partner feed / onchain evidence + source governance`

where possible.

Before serious public monetization/large-scale ingestion, get a proper legal review for:

- data aggregation;
- database rights;
- copyright/media;
- trademarks/branding;
- affiliate disclosure;
- relevant jurisdictions.

This handoff is an operational architecture record, **not legal advice**.

# 20. PROPERTY MEMORY / HISTORY MODEL

Realty already has the beginning of append-only observation history.

The key idea is:

> a changed source value should create a new observation, not overwrite the fact that the previous observation once existed.

The early Fallwood changes demonstrated why this matters: marketplace price/yield/investor counts can change quickly.

Current/future history should distinguish:

- observation timestamp/source-check date;
- asset identity;
- source semantics;
- prior independent observation;
- price/share change;
- yield/return change;
- investor/listing/status change;
- provenance.

Do not create a smooth synthetic chart from one or two points.

If history is insufficient:

> **History building**

is correct.

Long-run history architecture should eventually separate:

- current snapshot;
- append-only raw/material observations;
- compact time-series/rollups;
- archival history.

# 22. CURRENT TECHNICAL WEIGHT / CAPACITY MODEL

Realty is intentionally lightweight relative to its product depth.

Through v0.7 it is primarily:

- static HTML;
- CSS;
- browser JavaScript;
- compact JSON data;
- localStorage state;
- source links;
- no dedicated Realty backend;
- no Realty-specific workflow/collector fan-out.

This is a feature, not a limitation at the current scale.

Scaling approach:

## Current / small-to-medium catalogue

- generated/static machine-readable datasets;
- client rendering;
- bounded filters;
- local state;
- source snapshots.

## Thousands of records

- pagination/lazy rendering;
