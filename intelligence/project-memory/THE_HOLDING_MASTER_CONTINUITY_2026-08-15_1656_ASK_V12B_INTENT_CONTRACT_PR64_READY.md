# 6. INTENT CONTRACT FIREWALL — CANONICAL DESIGN

Durable module:

`agents/console/intent-contract.js`

Version / contract identity:

**Intent Contract Firewall v0.1**

It is browser-safe and Node-testable.

A future model or deterministic parser may propose only a bounded structured envelope containing concepts such as:

- `intent`
- `entities`
- `timeframe`
- `comparison`
- `requestedMetric`

The firewall performs strict allow-list validation and returns either:

- a normalized, frozen, bounded intent envelope; or
- reject / fail-closed.

The firewall itself deliberately **cannot answer questions**.

Declared authority properties include:

- `canAnswer = false`
- `canSetConfidence = false`
- `canSelectSourcesAsTruth = false`
- `canExecute = false`
- `executionAuthority = none`

The contract explicitly rejects unknown/unapproved keys and authority-bearing payloads.

Forbidden candidate fields/classes include attempts to inject:

- answer text;
- `answer` / `text`;
- source truth;
- `source` / `sourceArtifacts`;
- answer confidence;
- `confidence` / grounded truth claims;
- execution / action instructions;
- transaction/signature fields;
- wallet/private-key/seed material;
- methodology mutation;
- policy mutation;
- authority / permission expansion.

This is the key architectural invariant:

> A language model may someday propose what the user appears to mean, but it may never decide what is true, which source is authoritative, how confident the answer is, or what capital action may be executed.
